# 评审器黄金集（benchmark）

> C4A 的 rubric 第一条是「**评审器质量——自动评审器/评测器的质量与可靠性**」。
> 一个评审器"能跑"和"判得准"是两件事。**能证明后者的只有一件事：
> 用一批缺陷已知的样本跑一遍，把误报与漏报数出来。**
>
> ```bash
> python scripts/run_benchmark.py          # 跑基准（退出码 0 = 无新回归）
> python scripts/run_benchmark.py --all    # 连不一致明细一起列
> python scripts/run_benchmark.py --json
> ```

---

## ⚠️ 先说清楚这个测试**不能**证明什么

**8 份样本是我自己造的，标注是我自己做的。**

这保证了「**评审器实现没跑偏**」——这正是我要测的。
但它**不证明「判据本身合不合理」**：我完全可能把一条错误的期望标得很自信。

再加一条必须说明的：

> **分值区间的具体数值，是首轮跑完后才定的。**
> 缺陷注入与期望结论（谁该被拦、谁该合格）在造样本时就定了，
> 但区间宽度是后配的。这是区间式断言的常规做法，
> **但它确实削弱了断言的强度**——如实说明，不粉饰。

**要真正解决这一点，需要非本人提交、且与真实评分对照过的样本。**
方案已为此预留：`skill_evaluator.py` 接受任意文件夹，
同学的**真实 C4 提交**到位后直接跑，结果回填进《评审报告》。当前没有，我不假装有。

## 样本设计：每份样本注入一个缺陷

**目录名就是注入的缺陷**——这是刻意的，让"这份应该在哪儿被拦下"一眼可见。

| 样本 | 注入的缺陷 | 期望结论 | 为什么这份值得测 |
|---|---|---|---|
| `FX01_优质提交` | 无（对照基线） | ✅ 合格 | 标尺：连它都不合格说明评审器太严 |
| `FX02_缺教学说明` | 五个必须文件少一个 | ⚠️ 待改进 | **不该被否决**——很多同学就是漏交一份文件，不是技能不行 |
| `FX03_写死绝对路径` | `D:\Users\yanpo\…` | 🚫 不合格 | **看起来很好的一份**：五件齐全、写得很认真。只有确定性检查能发现别人根本跑不起来 |
| `FX04_私有依赖` | 内网服务 + 个人密钥 | 🚫 不合格 | 同类但更隐蔽——不是路径问题，是"需要我的密钥" |
| `FX05_只有文档` | 没有任何可执行产物 | 🚫 不合格 | 「可执行」是 C4 的硬要求 |
| `FX06_包结构错` | `.skill` 里 SKILL.md 埋在子目录 | ✅ 合格（扣分） | **故意不设成否决项**——它可能在某些宿主里仍能工作，判死刑太重。用来验证"扣分"与"否决"的边界 |
| `FX07_IO不明确` | 没有"输入…输出…" | ✅ 合格（IO 分低） | 说了很多（"非常好用"），但输入输出一个字没讲 |
| `FX08_日志是流水账` | AI 日志只有一句话 | ✅ 合格（aiUsage 低） | **这一条真正的判定应由 LLM 层做**，规则层只给下限——用来盯"规则层会不会给它高分" |

## 口径定义

| 术语 | 定义 | 伤害 |
|---|---|---|
| **否决项·误报** | 判了「不合格」，但样本其实没有该缺陷 | **冤枉一个认真交作业的同学**——且"不合格"是不可逆的负面判定，**伤害最大** |
| **否决项·漏报** | 样本明明写死了绝对路径，没被拦 | 让一个别人根本跑不起来的提交过关 |
| **一致性** | 完整性命中数、结论、缺失文件判定是否与期望一致 | — |
| **分值落点命中率** | 条件分与维度分是否落在期望区间内 | 区间刻意留宽——窄区间的通过只说明调参调得好，不说明判得准 |

## 用黄金集抓到的真 bug（这是它存在的意义）

基准建起来之前，评审器有 4 个问题。**其中第 1 个最危险：**

| # | 问题 | 为什么危险 |
|---|---|---|
| 1 | **`hard_gates` 从未被执行** —— 在 `rubric.json` 里定义了三个硬门槛，但代码只从 `condition.rules` 收集否决项 | **它不报错。** 程序正常退出、正常产出报告，只是**安静地少判了一件事**。一份写死路径的提交会被判成合格 |
| 2 | 绝对路径正则转义层数写错（要求两个连续反斜杠） | 整条检查失效 |
| 3 | 放宽后 URL 里的 `s:/` 被误判成绝对路径 | **每一份带链接的提交都会挂** |
| 4 | 报告出现「🚫 不合格，可复用 76.2%」的自相矛盾读数 | 76.2% 是"没踩坑的否决项拿满分"的加权产物，不是"可复用成立" |

四个问题都是拿"造样本时的意图"去对照输出才发现的。

## 加一个样本

在 `fixtures/` 下建一个目录，**目录名写明注入的缺陷**，然后在 `golden_set.json` 的
`cases` 里加一条：

```jsonc
{
  "id": "FX09",
  "fixture": "FX09_交付物为空壳",
  "author": "Someone",
  "title": "文件都在但内容全是占位",
  "expect_completeness_hits": 5,
  "expect_blockers": [],
  "expect_verdict": "待改进",
  "expect_condition_bands": {"verifiable": [0, 50]},
  "rationale": "为什么这样标注——这一栏比标签本身更重要"
}
```

**一条纪律**：`expect_*` 要依据**你自己注入的缺陷**来写，
不许跑一遍看了输出再回头改。否则测的是"评审器和它自己一致"，毫无意义。

## 基线

`baseline.json` 记录当前水平。CI 对比规则是：

- 否决项误报数 / 漏报数 / 不一致总数 **变大** → 报红
- 一致性 / 落点命中率 **下降** → 报红
- 只是"和之前一样" → 绿灯

**一跑就红的灯会被习惯性忽略。** 所以拒绝标准是"变差"，不是"有问题"。
